# Cloudflare R2 (candidata)

El transporte es configurable; no se cambia el almacenamiento de una instalación
existente al actualizar las imágenes. MinIO/S3 conservan POST por defecto. R2 no
admite el POST multipart firmado: usar PUT binario mediante su API S3.

## Configuración

Preparar manualmente un bucket **privado** y credenciales S3 restringidas a ese
bucket (lectura/escritura de objetos y los permisos mínimos necesarios para HEAD,
copiar y borrar objetos). Guardarlas en el gestor de secretos, nunca en Git.
No usar el token de administración global de Cloudflare como secret S3.

```dotenv
S3_UPLOAD_METHOD=PUT
USE_MINIO=0
AWS_REGION=auto
AWS_S3_ENDPOINT_URL=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
AWS_S3_BUCKET_NAME=<BUCKET>
AWS_ACCESS_KEY_ID=<desde-gestor-de-secretos>
AWS_SECRET_ACCESS_KEY=<desde-gestor-de-secretos>
SIGNED_URL_EXPIRATION=300
```

Usar el endpoint S3 de la jurisdicción correspondiente; no sustituirlo por r2.dev
ni un dominio público personalizado: los enlaces llevan firma sobre el host y la
ruta exactos. API y workers deben recibir la misma configuración. PUT omite ACLs
de objetos, que R2 no soporta. Crear el bucket antes de arrancar Plane; no depender
de que las credenciales de aplicación puedan administrar buckets.

El Compose base sigue incluyendo MinIO y sus volúmenes: **no eliminarlos ni
ejecutar `down -v`**. Seleccionar R2 es una operación del operador, no del CI.

## CORS del bucket

Ejemplo para un origen de Plane; reemplazar por los orígenes HTTPS exactos de web
y Sites si son distintos. CORS no es autorización ni un límite de tamaño.

```json
[
  {
    "AllowedOrigins": ["https://plane.example.com"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

El cliente manda el archivo crudo, sin FormData para PUT y sin cookies de Plane.
Content-Type debe coincidir exactamente con el autorizado. El navegador genera
Content-Length a partir del archivo: JavaScript no debe intentar fijar ese header
prohibido. No modificar ni normalizar la URL firmada.

## Seguridad y validación

Los endpoints mantienen sus comprobaciones de usuario, workspace, proyecto,
entidad y MIME permitido. El backend rechaza tamaños inválidos o superiores a
FILE_SIZE_LIMIT, firma tipo y **longitud exacta** y vuelve a comprobar el objeto
con HEAD antes de marcarlo subido. Un objeto ausente o diferente no se confirma.
No se permiten cambios de size/type mediante atributos editables posteriores.

Content-Type firmado no demuestra el contenido real del archivo ni reemplaza
antivirus. Se mantienen las reglas existentes de descarga segura. Las URLs son
capacidades reutilizables hasta expirar; no registrarlas ni compartirlas. Un
usuario puede sustituir bytes de igual tamaño/tipo durante esa ventana: no se
presenta PUT como operación de un solo uso.

CI prueba firmas reales y rechazos de tamaño/tipo contra un S3 compatible
aislado, además de permisos y clientes; esto **no equivale a una prueba real en
una cuenta R2**. Antes de habilitar R2, verificar en un bucket de prueba privado:
preflight CORS, upload correcto, firma expirada, MIME distinto, tamaño distinto,
confirmación de objeto ausente, descarga y borrado. No aceptar solo validaciones
frontend ni HEAD como sustituto del rechazo del tamaño firmado por el proveedor.

## Migración y rollback (procedimiento; no ejecutado automáticamente)

La configuración del bucket es global, no hay resolución automática por objeto
entre dos proveedores. Cambiar a un bucket vacío rompe los enlaces existentes.

1. Registrar versión y digests previos, configuración protegida y backups
   consistentes de DB y objetos. Probar restore aislado.
2. Preparar R2/CORS y ensayar sin datos productivos. Verificar también uploads
   backend, exportaciones, avatares, adjuntos y Sites.
3. Planificar una ventana sin escrituras y detener productores. Copiar mediante
   una herramienta revisada, preservando **todas las claves y Content-Type**;
   cotejar tamaños, recuentos y checksums compatibles. No asumir que ETag siempre
   es MD5. Este cambio de código no ejecuta ninguna copia ni migración.
4. Solo tras verificar la copia, cambiar la configuración conjunta de API y
   workers, usar las nuevas imágenes y probar antes de reabrir escrituras.
   Conservar MinIO, sus credenciales protegidas y sus volúmenes intactos.
5. Rollback antes de nuevas escrituras: volver a imágenes/configuración anteriores.
   Si hubo escrituras en R2, cerrar nuevamente el tráfico y reconciliar primero
   los objetos nuevos/modificados y los cambios de DB; volver simplemente a
   MinIO perdería acceso a esos objetos. Nunca restaurar una DB antigua sobre
   datos vivos sin el procedimiento de recuperación acordado.

Para revertir únicamente PUT, MinIO/S3 pueden seguir con POST. No volver a una
versión que solo soporte POST mientras el proveedor activo siga siendo R2.
No se requiere una migración de esquema para esta funcionalidad.
